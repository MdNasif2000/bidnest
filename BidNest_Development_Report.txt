Introduction

This report documents my individual development of BidNest, a web-based student accommodation bidding platform built as part of my university coursework. The idea came from a genuine frustration I noticed among students — finding off-campus housing in the UK is often stressful, unstructured, and heavily skewed in favour of landlords. Existing platforms like Rightmove and SpareRoom are built for the general rental market and offer very little that is tailored to students specifically.

BidNest aims to change that by giving students the ability to bid on properties, negotiate directly with landlords, sign digital contracts, and communicate through a built-in messaging system — all within one platform. As the sole developer, I was responsible for every layer of the system: database design, backend logic, frontend templates, real-time features, and deployment configuration.

This report walks through how the project evolved over six months, the decisions I made along the way, the challenges I ran into, and what I learned from the experience.


────────────────────────────────────────────────────────────────────────────────

Project Overview

BidNest is a full-stack web application designed specifically for the UK student housing market. The platform supports three types of users — students, landlords, and administrators — each with their own set of features and permissions.

Students can search and filter properties, place bids, negotiate counter-offers, sign contracts digitally, message landlords in real time, save favourite properties, post accommodation seeking ads, and leave reviews. Landlords can list and manage properties, review and respond to bids, generate contracts, communicate with students, and view their ratings. Administrators have access to a Django admin panel where they can oversee all users, properties, bids, contracts, and contact form submissions.

The platform was designed with a real-world use case in mind. Rather than building something generic, I tried to think through the actual journey a student goes through when looking for accommodation — from browsing listings to signing a contract — and make each step as smooth as possible.

One of the more distinctive features is the bidding and counter-offer system. Instead of a fixed rent price, landlords set a starting bid and students can place offers. The landlord can then accept, reject, or counter with a different amount. If the student accepts the counter-offer, a contract is automatically generated. This negotiation flow is something I had not seen implemented in any existing student housing platform, which made it one of the more interesting parts of the project to build.

The project also includes a real-time messaging system using WebSockets, an in-app notification system, a contract termination workflow, and a review system for landlords. Some features — such as Stripe payments and DocuSign e-signatures — are configured and ready for integration but are marked as "to be implemented" in the current version, as they require live API credentials and are beyond the scope of the academic submission.

Technology Stack

The backend is built with Django 5.1.5, using Python as the primary language. I chose Django because of its built-in admin panel, ORM, authentication system, and the speed at which you can get a structured project running. For a solo project with a lot of moving parts, Django's "batteries included" philosophy was genuinely useful.

The database is SQLite for development, with PostgreSQL configuration available for production. SQLite requires zero setup and is perfectly adequate for a project at this stage. The frontend uses Django's template engine with plain HTML, CSS, and vanilla JavaScript — no React or any frontend framework. This kept things simple and meant I did not have to manage a separate frontend build process.

Real-time messaging is handled through Django Channels with WebSockets, backed by Redis as the channel layer. Background tasks — specifically the automated contract expiry notifications — are managed with Celery and Redis. Static files are served using WhiteNoise, and the project is configured for deployment with Gunicorn as the production server.

Third-party integrations configured in the project include Stripe for payments, DocuSign for e-signatures, and Onfido for document verification. These are set up in settings.py and the .env configuration but are not yet live, as they require production API keys.

Month-by-Month Development Breakdown


Month 1: Planning, Research & Project Setup

The first month was mostly about figuring out what I was actually building and making sure the foundation was solid before writing any real application code. I had the idea for BidNest from early on, but turning a rough concept into a structured plan took more time than I expected.

I started by writing a feasibility study that covered the technical, economic, legal, and operational aspects of the platform. This was useful not just as a document but as a thinking exercise — it forced me to be specific about what the system needed to do, who it was for, and what risks were involved. The legal section in particular made me think carefully about things like GDPR compliance, the validity of digital contracts under UK law (Electronic Communications Act 2000), and the need to use FCA-authorised payment processors rather than handling funds directly.

After the feasibility work, I set up the Django project. I created the virtual environment, installed the core dependencies, and structured the project into separate Django apps from the start:

- accounts — user management, profiles, reviews
- properties — property listings, search, accommodation requests
- bidding — bids, counter-offers, bid history
- messaging — conversations, real-time chat
- payments — payment processing (configured, not yet live)
- contracts — contract generation, signing, termination
- notifications — in-app notification system
- api — REST API endpoints

Separating the project into apps this way was a deliberate decision. It keeps each area of functionality self-contained, makes it easier to find and fix bugs, and means that if one part of the system needs to change, it does not necessarily affect everything else. I had seen projects where everything was crammed into one app and it became very difficult to navigate, so I wanted to avoid that from the beginning.

I also set up the environment variable configuration using python-decouple, created the .env.example file, and configured the settings.py to support both development (SQLite, DEBUG=True) and production (PostgreSQL, security headers) environments. Version control was set up with Git from day one.

By the end of the month, the project skeleton was in place, the apps were registered, and I had a clear picture of what needed to be built.


Month 2: Database Design & Core Models

With the project structure in place, month two was focused entirely on designing and building the database layer. This was probably the most important phase of the whole project — getting the data models right early on saves a lot of pain later. I spent a good amount of time thinking through the relationships between models before writing any code.

The first model I built was the custom User model in the accounts app. Django's default User model does not support multiple user types, so I extended AbstractBaseUser to add a user_type field (student, landlord, admin) and made email the primary login identifier rather than username. This decision affected almost everything else in the project, since every other model references the User model in some way.

From there I built out the related profile models — StudentProfile and LandlordProfile — each linked to the User model via a OneToOneField. These store role-specific information like university and course for students, and business name and registration details for landlords.

The Property model was the most complex to design. It needed to capture everything a student might want to filter on: property type, room type, bedrooms, bathrooms, furnishing, amenities (WiFi, parking, garden, disabled access), bills included, pets allowed, location details including postcode, and pricing fields for starting bid, current bid, rent per month, and deposit. I also added a views_count field and an is_active flag so landlords could deactivate listings without deleting them.

The Bid model was designed to support the full negotiation flow. It stores the bid amount, a status field (pending, accepted, rejected, withdrawn, counter_offered), an optional message from the student, and a counter_offer_amount field for when the landlord proposes a different price. I also created a BidHistory model to keep a complete audit trail of every action taken on a bid.

The Contract model uses on_delete=models.PROTECT on the property foreign key, which means a property cannot be deleted if it has an active contract. This was an intentional design decision to protect data integrity — I did not want a landlord to be able to accidentally delete a property that a student had a live contract on.

Other models built this month included Conversation and Message for the messaging system, Notification for in-app alerts, Review for the landlord rating system, AccommodationRequest for students to post what they are looking for, SavedProperty for bookmarking listings, and ContactMessage for the contact form.

I ran the initial migrations at the end of the month and verified the schema using Django's admin panel. Seeing all the tables created correctly and the relationships working as expected was a good sign that the design was sound.


Month 3: Building the Bidding & Property System

Month three was where the platform started to feel like an actual product. I built out the two most central features: the property listing and search system, and the bidding and negotiation workflow.

For properties, I built views for listing, detail, add, edit, and delete. The property list view was more involved than it sounds — it needed to support a wide range of filter parameters (location, price range, bedrooms, bathrooms, property type, room type, furnishing, amenities, bills included, pets allowed) while keeping the URL clean and the filters persistent across page loads. I handled this by reading all filter values from request.GET and passing them back to the template as context, so the form fields stay populated after a search is submitted. The view only returns results when at least one search parameter is present, which avoids loading every property in the database on the initial page load.

The property detail page shows full property information, images, landlord details, and includes tabs for ad details and messaging. I also built the image upload system, allowing landlords to add multiple images per property with captions.

The bidding system took the most thought to get right. The place_bid view validates that the bid amount is at or above the starting bid, that the property does not already have an active contract, and that the student does not already have a pending bid on the same property. When a bid is placed, a notification is sent to the landlord automatically.

The landlord can then accept, reject, or make a counter-offer. Accepting a bid triggers contract generation — the system automatically creates a Contract record linked to the bid and property, and sends notifications to both parties. Rejecting a bid updates the status and notifies the student. Counter-offers set the bid status to counter_offered and store the proposed amount, then notify the student.

On the student side, when a counter-offer is received, they can accept or reject it. Accepting a counter-offer was a bug I had to fix — the property's current_bid field was not being updated when the counter amount was accepted. I fixed this by explicitly updating the property's current_bid in the accept_counter_offer view and also rejecting any other pending bids on the same property at that point.

I also built the accommodation seeking ads feature this month — a separate section where students (or any user) can post what they are looking for, including budget, location preference, room type, furnishing preference, and a "buddy up" option for students interested in finding flatmates. These ads are displayed on a public listing page with pagination and clickable cards.


Month 4: Contracts, Messaging & Real-Time Features

Month four covered two of the more technically challenging parts of the project: the contract system and real-time messaging.

The contract system needed to handle several states: draft, pending_signatures, active, terminated, and expired. Contracts are auto-generated when a landlord accepts a bid, pre-filled with the property details, bid amount, and both parties' information. Both the landlord and student then need to sign digitally — in the current implementation this is handled through a sign_contract view that records the signature and updates the contract status. When both parties have signed, the status moves to pending_signatures (awaiting payment activation).

I also built the contract termination workflow. Either party can request early termination by providing a reason, a proposed termination date, and a notice period. The other party receives a notification and can approve or reject the request. If approved, the contract status changes to terminated. The termination date must fall between the contract start and end dates, which is validated on both the frontend and backend.

For automated contract expiry notifications, I set up Celery tasks that run daily and check for contracts expiring in 30, 7, and 0 days. Both the landlord and student receive in-app notifications at each of these intervals. This required configuring Celery with Redis as the broker and using django-celery-beat for scheduling.

The messaging system was built using Django Channels and WebSockets. Each conversation is between two users and messages are delivered in real time without needing to refresh the page. The WebSocket consumer handles connecting, receiving messages, saving them to the database, and broadcasting to the conversation group. I also built the inbox view, conversation detail view, and a delete conversation feature.

One issue I ran into was a variable name conflict — Django's messages framework uses the name messages, which clashed with the chat messages queryset in the conversation template. I resolved this by renaming the queryset to chat_messages in the view context.

The unread message count badge in the navigation bar updates via an AJAX call to a dedicated endpoint every 60 seconds, so users can see when new messages arrive without being in the inbox.


Month 5: Notifications, Reviews & Frontend Polish

By month five, the core functionality was working. This month was about completing the remaining features and making the frontend feel polished and consistent.

The notification system was built to support multiple notification types: bid received, bid accepted, bid rejected, counter-offer received, contract generated, contract signed, contract expiring, termination requested, termination approved, review received, and review responded. Each notification stores a link to the relevant page so users can click through directly. The bell icon in the navigation shows an unread count badge that updates via AJAX, styled to match the messaging badge.

The review system allows students to rate and review landlords after having an active or completed contract with them. Reviews include a 1–5 star rating and a written comment. Landlords can respond to reviews, and students receive a notification when a response is posted. I built the star rating interaction in JavaScript — stars highlight on hover and the selected rating is stored in a hidden input field. Reviews display on the landlord's public profile page, and the landlord's average rating is calculated and shown alongside their profile information.

On the frontend side, I spent time making the property listing page more usable. The filter sidebar slides in from the left and includes all the filter options with persistence — values stay filled after applying filters and only reset when the user clicks "Clear Filters". I also fixed the property type filter checkboxes to match the actual model choices (Whole Property and Room), removed filter options that did not correspond to any database field, and ensured that all filter parameters are properly applied in the backend query.

I also built the accommodation request detail page with a "Send Message" button that starts a conversation between users, and added a delete option for users to remove their own seeking ads. The navigation "How it Works" link was updated to use a full URL with an anchor so it works correctly from any page, not just the homepage.

The base template was updated throughout this month to keep navigation links consistent, add unread count badges for both messages and notifications, and ensure the layout worked correctly across all pages.


Month 6: Testing, Bug Fixing & Final Review

The final month was dedicated to testing everything end to end, fixing the bugs that came up, and making sure the codebase was clean and well-organised.

I went through every major workflow manually: registering as a student and landlord, posting a property, placing a bid, going through the counter-offer flow, generating and signing a contract, requesting termination, sending messages, writing a review, and posting an accommodation seeking ad. This process surfaced a number of issues that I had not caught during development.

One of the more significant bugs was in the counter-offer acceptance flow — when a student accepted a counter-offer, the property's current_bid field was not being updated, so the listing still showed the old bid amount. I fixed this by updating the property in the accept_counter_offer view and also rejecting any other pending bids on the same property at that point, which is the correct behaviour.

Another issue was with the filter sidebar — several filter fields (location, property type checkboxes, room type checkboxes) were resetting after the user applied filters, even though they had not clicked "Clear Filters". This was caused by missing hidden inputs in the property type radio form and the main search form. I added the missing hidden inputs to all three forms so that every filter value is preserved across submissions.

I also found and removed duplicate filter sections in the sidebar (Bills Included, Pets Allowed, and Must Have had been duplicated), and removed a "Rooms For" filter that referenced a field that does not exist in the Property model.

Towards the end of the month I cleaned up the documentation. I deleted a large number of redundant markdown files that had accumulated during development and replaced them with a single comprehensive COMPLETE_GUIDE.md covering setup, architecture, workflows, testing, troubleshooting, and deployment. I also ran python manage.py collectstatic after every significant change to ensure static files were up to date.

The project was reviewed against the original feasibility study to check which features had been implemented and which were still pending. The core platform — bidding, contracts, messaging, notifications, reviews, and accommodation ads — is fully functional. Payment processing (Stripe), e-signatures (DocuSign), and document verification (Onfido) are configured and ready but require live API credentials to activate.

Critical Evaluation

Looking back at the project as a whole, I think the strongest part of what I built is the bidding and negotiation system. The flow from placing a bid to counter-offer to contract generation works reliably, and the bid history model means there is a complete audit trail of every action. This was the most original part of the platform and the feature that most clearly differentiates BidNest from existing student housing sites.

The database design also held up well throughout development. Separating the project into seven Django apps from the start meant that when I needed to make changes in one area — say, the contract termination workflow — I was not having to untangle dependencies across the whole codebase. The use of on_delete=models.PROTECT on the contract-to-property relationship was a good decision that prevented data integrity issues.

That said, there are things I would do differently. The filter system on the property listing page went through several iterations because I had not fully thought through which filter parameters needed to be preserved across which forms. If I had mapped out all three forms and their interactions on paper before writing the template, I would have saved a lot of debugging time. The same applies to the messaging variable name conflict — a quick review of Django's reserved context variable names before starting would have caught that immediately.

The real-time messaging works, but it requires Redis to be running locally, which adds a setup dependency that is not ideal for a development environment. In hindsight, I could have used Django's in-memory channel layer for development and only required Redis in production, which would have made the project easier to run out of the box.

The payment and e-signature features being incomplete is the most obvious gap in the current version. These are genuinely complex integrations that require live API credentials, webhook handling, and careful testing — more than was feasible within the project timeline. The architecture is in place for both, and the configuration is ready, but they remain the most significant items on the "to be implemented" list.

On the frontend, the decision to use Django templates with vanilla JavaScript rather than a framework like React kept things simple and meant I could move quickly. However, there are parts of the UI — particularly the filter sidebar and the real-time message updates — where a component-based approach would have been cleaner. For a project of this scale it was the right call, but for a larger team or a longer timeline, a proper frontend framework would be worth the setup cost.

Personal Reflection

This project pushed me further than I expected. Going into it, I had a reasonable understanding of Django and had built smaller projects before, but BidNest was the first time I had to design and build a complete system from scratch — one with multiple user roles, real-time features, background tasks, and a non-trivial business logic layer.

The part I found most challenging was not any single feature but the way everything connects. When you are building a bidding system, you are not just writing a view that saves a form — you are also thinking about what notifications need to be sent, what the contract system needs to know, how the property listing should update, and what happens if the student withdraws the bid before the landlord responds. Keeping all of those threads in mind at once, and making sure changes in one part of the system did not break something else, required a level of planning I had not needed before.

I also learned a lot about the importance of testing as you go rather than leaving it to the end. Several of the bugs I found in month six — the counter-offer not updating the property bid, the filter values resetting — would have been caught much earlier if I had been more systematic about testing each feature immediately after building it. Going forward, I want to build the habit of writing at least basic manual test cases for each feature before moving on to the next one.

Working solo on a project this size also gave me a new appreciation for documentation. When I came back to a part of the codebase after a few weeks away, I sometimes had to spend time re-reading the code to remember what it was doing and why. Adding comments and keeping the COMPLETE_GUIDE.md up to date helped, but I could have been more consistent about it throughout the project rather than doing a big documentation pass at the end.

On the positive side, I am genuinely proud of what the platform does. The bidding flow, the contract lifecycle, the real-time messaging, the notification system — these all work together in a way that feels like a real product rather than a university exercise. That is something I did not take for granted, and it has given me a lot of confidence going into future projects.


────────────────────────────────────────────────────────────────────────────────

Conclusion

Over six months of solo development, I designed and built BidNest from an initial concept into a functioning full-stack web platform. The system covers the complete student accommodation journey — from searching and filtering properties, through bidding and negotiation, to contract generation, digital signing, and real-time communication between students and landlords.

The project gave me hands-on experience with Django's full ecosystem: custom user models, complex ORM queries, WebSocket integration with Django Channels, background task scheduling with Celery, REST API design with Django REST Framework, and production configuration with WhiteNoise and Gunicorn. Beyond the technical skills, it taught me how to think about a system as a whole — how the pieces connect, where the failure points are, and how early design decisions ripple through everything that comes after.

The platform is not finished in the sense that payment processing, e-signatures, and document verification still need live API integration. But the architecture is in place, the configuration is ready, and the core functionality works reliably. BidNest is a solid foundation that could be extended into a production-ready product with further development.

This has been the most substantial piece of software I have built independently, and it has been a meaningful step forward in how I approach development work.
